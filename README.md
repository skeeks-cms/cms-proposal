# skeeks/cms-proposal

Единый реестр «Предложения» для CRM SkeekS CMS. Два вида:

- **КП** — коммерческое предложение: версии, позиции с разделами, шаблоны,
  PDF, страница КП по личной ссылке с учётом просмотров, «Принять» и
  «Задать вопрос»;
- **Презентация** — страница сайта (своего или любого, например
  `/works/sfery/plitka`) и короткий текст менеджера: личная ссылка
  засчитывает просмотр и сразу переводит клиента на страницу.

Отправка, личные ссылки, учёт просмотров, отсев проверок ссылок, лента,
уведомления и задача менеджеру при первом открытии — общие для обоих видов.
Этап 3 проекта коммуникаций, согласованная архитектура —
`skeeks/cms-communication/ARCHITECTURE.md`, разделы «КП (реестр
предложений)», «Единый реестр „Предложения“: КП и Презентация» и «Отправить
клиенту».

## Страница КП для клиента

- Адрес — `/~kp/<код>` (правила `urlManager` в `config/web.php`); код
  отправки — единственный доступ, как у страницы счёта `cms-shop`. Ссылка
  показывает ту версию, с которой её отправили; `?v=latest` — новейшую
  отправленную, действия страницы (`seen`, `accept`, `ask`, `pdf`) берут ту же.
- Своя раскладка `views/proposal/layout.php` без `beginPage()/head()/endBody()`:
  пакеты сайта вешают на события View скрипты темы, баннер cookie, счётчики и
  ключевые слова, а страница отдаётся в `Response::$content`, поэтому
  `cms-seo` не дописывает в неё счётчики. `noindex` в заголовке и в meta,
  `Referrer-Policy: no-referrer` (код в адресе), `Cache-Control: no-store`.
- Оформление — светлое, акцентный цвет и логотип из шаблона документов сайта
  (как PDF); на узком экране позиции идут карточками.
- Просмотр засчитывается запросом `POST …/seen` из скрипта страницы, когда
  она 1,5 секунды видна (`visibilityState`); `curl`, почтовые проверки и
  предпросмотр мессенджеров его не делают, а известные роботы
  (общий список `LinkChecks::ROBOT_PATTERNS` пакета `skeeks/cms-communication`,
  `ProposalViews::BOT_PATTERNS` — тот же) записываются в историю без счёта.
- Сигнал передаёт признаки браузера (`navigator.webdriver`, число языков,
  размер экрана): проверки ссылок в автоматическом браузере
  (`LinkChecks` пакета `skeeks/cms-communication`) не засчитываются.
- Сигнал «страницу увидели» и признаки браузера — общий скрипт
  `skeeks/cms-communication` (`LinkSignalAsset`, `link-signal.js`), его же
  использует учёт переходов по ссылкам из писем; раскладка печатает его
  перед `proposal-page.js`. Метки адреса перехода —
  `LinkMarks::addParams()` (`PresentationLinks::addUtm()` вызывает его).
- Письмо с предложением: другие ссылки письма на наши сайты получают
  `utm_campaign=proposal-<номер>` (`ProposalSendable` реализует
  `SendableMarksInterface`) и личный код письма — переходы по ним пишет
  в ленту `cms-communication`. Личная ссылка `/~kp/…` не размечается.

## Презентация: страница-переход

- Та же ссылка `/~kp/<код>` и то же оформление. Скрипт, как только
  страница 0,4 секунды видна, шлёт `POST …/seen` и затем (или через 2,5
  секунды без ответа) заменяет страницу адресом презентации
  (`location.replace`: «Назад» не возвращает на переход). Сотрудник CRM
  видит, что переход не засчитан, и переходит через 3 секунды.
- Адрес — только `CmsProposal::$target_url`, никогда не параметр ссылки:
  страница не открытое перенаправление. К адресу добавляются
  `utm_source=crm`, `utm_medium=<канал>`, `utm_campaign=proposal-<номер>`
  (`PresentationLinks::addUtm()`, уже указанные метки и `#фрагмент`
  сохраняются).
- Без скриптов (роботы, `curl`) просмотра и перехода нет — только ссылка
  «Перейти». После срока действия — «Ссылка больше не действует» и
  контакты ответственного, без перехода.
- «Принять», «Задать вопрос» и PDF для Презентации отвечают 404.

## Задача менеджеру при первом открытии

- `ProposalTasks::onFirstView()` вызывается из `ProposalViews` после
  первого засчитанного просмотра отправки, для КП и Презентации; ошибка
  задачи пишется в журнал и не мешает клиенту.
- Задача ядра `CmsTask` себе (`created_by` = исполнитель, сразу «Принята»;
  на странице клиента никто не вошёл), `plan_start_at` — не раньше чем
  через 31 минуту (правило модели) в рабочем периоде сегодня, иначе начало
  ближайшего рабочего периода по `work_shedule` сотрудника.
- Связь задачи с предложением — `cms_proposal_task`: по ней ищется открытая
  задача ответственного по предложению (новая не ставится) и показывается
  «Клиент открыл: …» в карточке задачи. Закрытая задача не мешает новой при
  первом открытии следующей отправки. У общей Презентации открытая задача
  ищется по предложению и клиенту отправки: каждому открывшему клиенту —
  своя задача.
- Настройка «Задача менеджеру при первом открытии»
  (`ProposalSettings::$taskOnFirstView`, по умолчанию включено) — кнопка
  «Настройки» в разделе у администратора. Для письма кампании рассылок решает
  настройка кампании «Задача менеджеру, когда клиент открыл предложение»
  (`Campaigns::taskOnOpen()` по сообщению отправки).

## Чтение для ИИ-клиентов (MCP/REST)

Если установлен `skeeks/cms-mcp`, пакет добавляет инструменты чтения
(`src/mcp`, scope `cms.communication.read`, регистрация через `params['cmsMcp']`
в `src/config/common.php`):

- `cms_proposal_list` — КП и Презентации по клиенту (как блок «КП» карточки,
  `CmsProposalQuery::forRecord()`) или общий список с фильтрами;
- `cms_proposal_get` — карточка: позиции и итог версии КП или адрес страницы
  Презентации, отправки, честные открытия, вопросы клиента, принятие;
- `cms_proposal_library_get` — готовые общие Презентации и шаблоны КП.

События предложений в общей истории клиента описывает
`mcp\ProposalHistoryDescriber`, раздел `proposals` обзора клиента —
`mcp\ProposalOverviewContributor`. Видимость — `CmsProposalQuery::forManager()`.
Коды и личные ссылки отправок (`/~kp/`) не выдаются никогда: их открытие
засчиталось бы как открытие клиентом. Тест:
`PROPOSAL_MCP_TEST=local php tests/mcp-read.php` на локальном сайте с `cms-mcp`.

Действия ИИ (черновики писем и кампании с предложением) живут в
`cms-communication` (`services\AiActions`). Пакет даёт им две вещи:
`ProposalSendableSource` реализует `send\SendHistoryInterface`
(`lastSentAt()` — последняя отправка предложения лиду, его компании или
клиенту: повторно за 30 дней ИИ его не предлагает), а запись ленты
«отправлено» хранит отметку «Подготовлено ИИ» письма (`data.ai`: клиент,
пользователь, изменено ли, `sent_by`, `sent_via` — отправлено ИИ через API);
её показывают лента и отправки в карточке предложения (по письму отправки).
`ProposalSendable` реализует `send\SendRefusalInterface` (`getSendRefusal()` —
`ProposalSends::refusal()`: истёк срок, нет страницы, пустое КП), чтобы
проверка черновика через API отказала до письма; `states()` отдаёт номер
отправки, просмотры и отдельно проверки ссылок почтовыми службами.

Презентации через API (`mcp\ProposalActionToolProvider`, scope
`cms.proposal.write`, логика — `services\Presentations`, та же модель и
видимость, что в форме «Предложения»):

- `cms_proposal_presentation_create` — название, `target_url` (полный адрес или
  путь сайта), вводный текст `message`, клиент (`client: {type, id}` —
  лид, компания, сделка, клиент-человек) или без него — общая для всех,
  `valid_until` (ГГГГ-ММ-ДД), `responsible_id` (по умолчанию OAuth-сотрудник).
  Презентация той же страницы для того же клиента (или для всех) — отказ с её
  id, `allow_duplicate=true` — создать всё равно. Общая сразу видна в
  `cms_proposal_library_get`.
- `cms_proposal_presentation_update` — только переданные поля; клиента у уже
  отправленной Презентации не меняет.

Без `confirm=true` оба только проверяют. Ответ — данные Презентации, как в
`cms_proposal_get` (id, номер, статус, ссылка на карточку).
